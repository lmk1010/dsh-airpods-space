# DSH 耳机空间（AirPods 语音控制插件）需求拆分

> 代码：`DSHub/dsh`（deepseek-harness 克隆，分支 `mk/airpods`，基线 fcc0ad4621 / 0.2.2-rc.1）
> 参考：`AI/ref/deepseek-harness`（只读，定期 pull）
> 状态标记：☐ 未开始 ◐ 进行中 ☑ 完成 ⚠ 有风险/待实机验证

## 0. 总体目标
按一下 AirPods → 说话 → 实时出字 → 自动发给 DSH / 执行语音命令；耳机连接时弹出跟 iOS 一样的连接动画。
主平台 macOS 桌面版，App 不在前台也能用；网页版能做多少做多少。

## 1. 技术选型（已定）
| 项 | 选择 | 理由 |
|---|---|---|
| 本地流式识别 | **sherpa-onnx OnlineRecognizer + streaming-paraformer-bilingual-zh-en** | 官方 SenseVoice 已经在用 `sherpa-onnx-node`，同一个运行时，下载链路（HF / HF-Mirror）可复用 |
| 本地二遍纠错 | SenseVoice（官方已有） | 说完后用整段音频重新识别一次，替换流式结果，准确率更高（FunASR 2-pass 思路） |
| 云端流式 | Provider 抽象，首发 **阿里云百炼 Paraformer-realtime / Fun-ASR-realtime（WebSocket）**，后续火山引擎（豆包）、讯飞、OpenAI Realtime | 用户自己填 Key |
| 耳机事件 | Swift 原生 helper（随 App 打包），通过 stdio JSON 和 Electron 主进程通信 | 系统蓝牙、媒体键、辅助功能这些 API 只有原生代码能调 |
| 连接弹窗 | Electron 透明、置顶、无焦点的浮窗 + 自绘 3D/SVG 动画 | macOS 没有系统级 AirPods 弹窗，要自己画；不用 Apple 官方素材（版权） |

## 2. 里程碑与任务

### M0 技术验证（先做，决定后面的路线）
- ☑ M0.1 编译 Mac 版（已装到 /Applications/DeepSeek Harness.app，0.2.2-rc.1，ad-hoc 签名）：`pnpm package:desktop:mac:arm64:unsigned`，装进 /Applications 能启动、能对话
- ☑ M0.2 （spikes/tools/restart-dev.sh；热更新没用，每次重建后重启）开发模式能跑（`pnpm start:desktop` 已经能启动「Harness Dev」，热更新待验证）：`pnpm dev:desktop`，改插件代码能热更新（开发过程实时可见）
- ☑ M0.3a 方案已定（2026-11-05 用户确认，见 耳机按压方案研究.md）：主路线是静音手势（3/4/Pro/Max，语音模式下）；辅助路线是语音模式和读回复时占用「正在播放」（所有型号，1/2 代靠双击）；兜底是全局快捷键
- ☑ M0.3 （结论：MPRemoteCommandCenter 加静音手势，见 耳机按压方案研究.md）**按压事件捕获实验**（需要你的 AirPods 实机按）：在 macOS 15.6 上分别测下面三种方式能不能收到「按一下」
  - a. CGEventTap 监听 NX_SYSDEFINED 媒体键（需要辅助功能权限）
  - b. MPRemoteCommandCenter + 声明自己是 Now Playing（不需要权限，但会和音乐 App 抢）
  - c. macOS 14+ AVAudioApplication 静音手势（只在麦克风开着时有效 = 通话模式）
  - 产出：每种方式 × 前台/后台 × 有没有音乐在播 的结果表 → 定主方案和降级方案
- ☑ M0.4 （IOBluetooth 加 system_profiler 约 0.1 秒；BLE 开盖广播）连接检测实验：IOBluetooth 连接/断开通知 + `system_profiler SPBluetoothDataType -json` 读型号 ProductID、左/右/盒电量，测从连上到拿到数据的延迟
- ☑ M0.5 （按压到开麦 207 ms；本地首字约 1.3 秒；阿里云复用连接时首字 0.98 秒）测各环节延迟（本地流式已测：加载 1–2s、RTF≈0.1、约 0.6s 出一次字，见 spikes/stream-bench；按压和开麦两段等实机）：按压 → 开麦（蓝牙切到通话模式 HFP 本身就有约 0.3–1s）→ 第一个字出来 → 最终结果，建立基线

### M1 原生 Helper（`native/airpods-helper`，Swift）
- ☑ M1.1 （packages/airpods/airpods-helper，swiftc 编出 arm64+x86_64 通用二进制，ad-hoc 签名）工程骨架：Swift Package，编成 universal binary，打包进 App 的 Resources，主进程用 spawn 拉起，stdio 收发行分隔的 JSON
- ☑ M1.2 （按地址去重；启动时系统重放的已连接设备不算新连接）事件 `device.connected / disconnected`：mac 地址、名称、ProductID、型号枚举
- ☑ M1.3 （系统读到的精确电量优先，BLE 的 10% 粒度只作兜底）事件 `device.battery`：左、右、盒电量，以及是否在充电（连上时读一次，之后每 60 秒或有变化时更新）
- ☑ M1.4 事件 `press`：静音手势（AVAudioApplication，回调标 @Sendable，只在状态真的变了时算一次按压）+ 正在播放（MPRemoteCommandCenter，只在语音模式或读回复时占用，结束就让出）；报出事件来源（mute / remote）
- ☑ M1.4b 冲突检测：CGGetEventTapList 找出拦截媒体键的进程；MediaRemote 私有接口查谁占着「正在播放」；发出 `conflict` 事件（App 名、pid、类型）
- ☑ M1.4c （状态位：0x04 广播这只在盒里，0x10 另一只在盒里，0x02 在耳朵上；在盒里的那只在充电，用来判断哪只在盒里；开盖计数 b[10]&7 用来过滤过时的转发；盒电量 0xF 表示盒子合着或离得太远）BLE 靠近配对广播（0x004C/0x07）：型号、左右耳和盒电量、充电状态、盖子状态、开盖计数；用「开盖计数字节变化」判断开盖，不用「第一次看到」；参考 Friday 的 mac-helper/sense.swift
- ☑ M1.5 事件 `ear`：入耳/摘下（拿得到就做，拿不到就砍）
- ☑ M1.6 权限查询和请求：辅助功能、麦克风、蓝牙，回报 `permission.status`
- ☑ M1.7 （HelperProcess 按 0.5/2/5/15/60 秒退避重启，超过次数显示 failed）Helper 崩溃后自动重启，指数退避；版本握手
